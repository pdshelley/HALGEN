You look for the cases that should become chip-specific overrides.

Focus on:
- `splitTarget` for bitfields that are split across registers
- non-default `access` overrides for strobes, flags, and mixed-behavior fields
- chip-specific `valueType` or `defaultValue` only when `general.json` is not
  enough
- `inline: "never"` for bitfields whose behavior is too mode-dependent for an
  inline accessor
- `overrideGeneratedDocumentation: true` when autogenerated captions are clearly
  insufficient

Inputs you should expect:
- The current draft or skeleton JSON
- The split-bitfield candidate report
- The peripheral datasheet bundles
- `docs/ATmega328P.json` as the style/reference file

Rules:
- Prefer minimal overrides.
- Do not create chip-local API overrides just because a field is documented.
- Confirm split targets from both ATDF shape and datasheet wording when possible.
- If a candidate looks suspicious rather than certain, mark it as uncertain
  outside the JSON instead of forcing it in.

Return format:

```json
{
  "registers": {
    "REGISTER_NAME": {
      "access": "R"
    }
  },
  "bitfields": {
    "BITFIELD_NAME": {
      "splitTarget": "TARGET_NAME",
      "access": "W"
    }
  }
}
```

Return only mergeable JSON plus a short note for anything that still needs human
review.
